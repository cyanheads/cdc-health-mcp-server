# CDC Health Statistics MCP Server

## Overview

Wraps the [CDC Open Data portal](https://data.cdc.gov/) (~1,080 datasets among ~1,480 catalog entries) via the [Socrata SODA API](https://dev.socrata.com/) to enable discovery, exploration, and querying of public health data. Covers disease surveillance, mortality, behavioral risk factors, vaccinations, environmental health, injury statistics, and more. No authentication required -- app token optional for higher rate limits.

The core challenge: ~1,080 datasets with heterogeneous schemas. The server provides a discovery-first workflow -- find the right dataset, inspect its schema, then query it -- rather than hard-coding knowledge of specific datasets.

A second, unrelated CDC system sits alongside it: **CDC WONDER**, reached by `cdc_query_wonder`. It answers national mortality questions directly -- deaths, population, and crude/age-adjusted rates from five mortality databases spanning 1999 through the current year, final and provisional, underlying-cause and multiple-cause -- with no catalog, no schema step, and its own protocol. Discovery-first applies to Socrata; WONDER is a single tool whose shape is fixed apart from the `database` selector.

**Dependencies**: `@cyanheads/mcp-ts-core`, Socrata SODA API v2.1 (public, optional app token), CDC WONDER's `datarequest` XML API (public, no auth). SODA3 (`/api/v3/views/{id}/query.json`) is available with mandatory auth but SODA 2.1 remains fully supported. Target SODA 2.1 for now -- no auth required for basic access.

## Tools

### `cdc_discover_datasets`

Search the CDC dataset catalog by keyword, category, tag, or asset type. Returns dataset IDs, names, truncated descriptions, a column count with a short column sample, update timestamps, and portal links. This is the entry point -- use before querying to find the right dataset for a question. Full column detail comes from `cdc_get_dataset_schema`.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `domain` | enum | No | CDC Socrata host to search: `data.cdc.gov` (default) or `chronicdata.cdc.gov`. Allowlisted -- any other host is rejected at input validation. Both values search the same catalog (see *The two hosts are one catalog* below). |
| `query` | string | No | Full-text search across dataset names and descriptions (e.g., "diabetes mortality", "lead exposure children"). |
| `category` | string | No | Filter by domain category, matched exactly (ignoring case) against the catalog's category vocabulary (a few dozen values) — `cdc_list_catalog_vocabulary` lists every value with its entry count. Common values: "National Center for Health Statistics", "NNDSS", "Vaccinations", "Public Health Surveillance", "Behavioral Risk Factors", "Motor Vehicle", "Maternal & Child Health". |
| `tags` | string[] | No | Filter by domain tags (e.g., ["covid19", "surveillance"]), matched case-insensitively against the catalog's ~1,600-value tag vocabulary (`cdc_list_catalog_vocabulary`) — see the tag semantics note below; multiple tags widen the result set rather than narrowing it. |
| `asset_types` | enum[] | No | Limit the search to these catalog asset types, spelled as `assetType` reports them: `dataset`, `filter`, `chart`, `map`, `story`, `file`, `href`. An entry matches when it is any one of them, and `totalCount` counts only those; `["dataset", "filter"]` returns just the entries with rows to query. Omitted or `[]` searches every type. |
| `limit` | number | No | Results to return (default 10, max 10,000). `offset + limit` must not exceed 10,000 — see the pagination note below. Above 10,000 rejects as `invalid_arguments`. |
| `offset` | number | No | Pagination offset for browsing beyond first page (max 9999). `offset + limit` must not exceed 10,000 — see the pagination note below. |
| `order` | enum | No | `relevance` or `dataset_id`. Defaults to `relevance` when `query` is set and `dataset_id` otherwise, at every `offset`; an explicit value always wins. `relevance` ranks the best matches first, but its order varies between calls, so paging a relevance search by `offset` can repeat or skip entries. `dataset_id` is a stable order whose offset pages walk every match exactly once. |

**Returns:** Array of `{ id, name, assetType, permalink, accessPoints, parentIds, description, category, tags, columnCount, columnSample, updatedAt, pageViews }`. `permalink` is the entry's page on the portal; `accessPoints` (`[{ label, url }]`, publisher labels in upstream order) is where a link (`href`) entry's external destination appears, and nowhere else; `parentIds` names the datasets a chart, map, filter, or story is built on (`resource.parent_fxf`). Each is absent when the catalog lacks it. `description` is converted to plain text and *then* truncated to 300 characters, so the budget buys visible text rather than the markup catalog entries arrive wrapped in; the whole text comes from `cdc_get_dataset_schema` with `full_description: true`. `columnSample` lists the first 8 column field names (the full list lives in `cdc_get_dataset_schema`). Includes `totalCount` for pagination.

**Decision: `limit` is the page, up to the Discovery API's own 10,000-entry window, with no cap below it.** A call that sets `limit` expects that many entries back, and a page that stops short reads as the end of the catalog. The API answers any `limit` at `offset=0` and both portals hold under two thousand entries, so the window already bounds the response and a lower clamp would only force extra calls. The one `notice` carries the empty-page text and the relevance-order warning, since a second write replaces the first.

**Decision: `order` defaults by whether `query` is set.** A keyword search wants its best match on the first page, and a walk of the catalog wants a stable order. Sorted by `dataset_id`, the first page of `"drug overdose deaths"` omitted `xkb8-kh2a` (VSRR Provisional Drug Overdose Death Counts), which `relevance` ranks first. The default never depends on `offset`: page 2 read under a different order than page 1 is neither walk. A blank `query` counts as unset. Relevance order differs between identical calls, not only across pages, so while matches remain past a relevance page the `notice` says so and names `order: "dataset_id"` as the way to walk every match.

**Non-dataset catalog assets:** the Discovery API returns `chart`, `map`, `story`, `file`, and `href` entries alongside `dataset` ones, each with a four-by-four ID, and none of the non-dataset types except `filter` has rows to query. `assetType` carries the catalog's own label, but it is descriptive, not a queryability test — a `filter` asset has real columns and queries normally, while `chart` and `map` assets report `viewType: "tabular"` with no columns at all. The signal that tracks real queryability is `columnCount === 0`, and the server keys its behavior off that rather than off the type, so the default search covers every type and the queryable `filter` entries stay in it. `asset_types` narrows the search on request: the values are sent as one comma-joined `only` parameter in their plural spelling (`datasets,filters`), because the API answers an unrecognized spelling with an empty page rather than an error, and the bare `dataset` form came back empty on some draws where the plural did not. Non-tabular entries stay useful: a file or link is reached through `permalink` and `accessPoints`, and a chart or map through the dataset its `parentIds` name.

**Tag semantics:** the Discovery API takes one `tags` parameter per value and unions them — a dataset matches when it carries any one of the listed tags, so each tag added returns more results, not fewer. Measured against `data.cdc.gov`: `covid19` alone matches 19 entries, `vaccination` alone 41, and the two together 59 (the two sets overlap in one dataset). Tag values match the catalog's own vocabulary, case-insensitively; a value no dataset carries matches nothing and leaves the count unchanged (`["covid19","zzzznotag"]` returns the same 19 as `covid19` alone), which is indistinguishable from a real tag with no matches. The other dimensions intersect: `tags=covid19` plus `categories=Vaccinations` narrows to 1, and `q=diabetes` plus `tags=covid19` likewise narrows to 1. `tags` is the only multi-value filter the server exposes where union and intersection are both plausible readings — `cdc_query_wonder`'s `age_groups` also unions, but a death falls in exactly one age group, so any-of is its only coherent reading.

**Pagination ceiling:** the Discovery API rejects a request with a nonzero `offset` whose `offset + limit` exceeds 10,000, with a 400 pointing at its deep-scrolling API. At `offset=0` it answers any `limit` (measured live: `limit=10001` and `limit=50000` return 200; `offset=1&limit=10000` and `offset=9901&limit=100` return 400). The bound is on the sum, which no pair of independent per-field maxima can express (`offset: 9999, limit: 5` clears both and still fails upstream), so the tool checks it in the handler, on the raw `limit`, and fails with `page_out_of_range` before the request. Both portals report ~1,480 catalog entries, so the ceiling is unreachable by legitimate paging.

**Error modes:**

| Error | Cause | Recovery |
|:------|:------|:---------|
| Empty results | No datasets match query/category/tags combination | A `category`/`tags` value is resolved against the catalog vocabulary and the notice names the closest values with their entry counts; with nothing close, broaden search terms, try fewer filters, or use `query` alone |
| Offset past `totalCount` | Valid search, but the page starts beyond the last result | Distinguished from a no-match in the returned notice, which names `totalCount`; lower `offset` below it |
| `page_out_of_range` | `offset` above 0 and `offset` plus `limit` above 10,000 | Rejected before the request. Lower `offset` or `limit` so their sum is at most 10,000; `offset` 0 takes any `limit` |
| `access_denied` (403) | Catalog refused the request | Permanent — do not retry. Drop category/tag filters and search with `query` alone |
| Rate limited (429) | Too many requests to Socrata Discovery API | Retry after brief delay. Consider using an app token for higher limits |
| `upstream_error` | A 5xx, an unreachable catalog, no complete answer within the 20-second request deadline, or a body that is not the JSON the endpoint serves | Retry once after a brief delay |

**Catalog API:** `GET https://api.us.socrata.com/api/catalog/v1?domains={domain}` where `{domain}` is `data.cdc.gov` (default) or `chronicdata.cdc.gov`.

### `cdc_get_dataset_schema`

Fetch the full column schema for a dataset -- names, data types, descriptions. Essential before writing queries against unfamiliar datasets. Also returns dataset name, description, row count, last-updated timestamp, and the provenance the publisher recorded: the period and area covered, the update cadence, a suggested citation, license, and attribution.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `domain` | enum | No | CDC Socrata host to fetch metadata from: `data.cdc.gov` (default) or `chronicdata.cdc.gov`. Either resolves any four-by-four ID (see *The two hosts are one catalog* below). |
| `datasetId` | string | Yes | Four-by-four dataset identifier matching `[a-z0-9]{4}-[a-z0-9]{4}` (e.g., "bi63-dtpu"). Obtain from `cdc_discover_datasets`. |
| `column_limit` | number | No | Columns to return (default 100). No maximum: it slices a schema already fetched whole, so a value at or above the column count returns every column. See *Wide schemas* below. |
| `column_offset` | number | No | Index of the first column to return (max 10,000), for continuing a previous call. |
| `full_description` | boolean | No | Return the dataset description whole (default `false`, which caps it at 4,000 characters). |

**Returns:** `{ name, description, descriptionTruncated?, descriptionLength?, rowCount, rowCountSource, updatedAt, parentId?, temporalCoverage?, updateFrequency?, geographicCoverage?, citation?, license?, attribution?, columns: [{ fieldName, dataType, description }] }`. `parentId` names the dataset a `filter` is a view of. The six publisher fields are the publisher's own text, trimmed and never parsed — `temporalCoverage` reads `2015-01-01/2026-05-31` on one dataset and `2019/present` or `N/A` on another, `updateFrequency` `R/P1M`, `Weekly`, or `No longer updated (dataset archived)` — and each is absent when the publisher recorded none. `updatedAt` is when the data last changed, which alone does not tell a monthly series from a closed one; `updateFrequency` does. They come from the `Common Core` section of the metadata document's `custom_fields` (`Temporal Applicability`, `Update Frequency`, `Geographic Coverage`), the `Data Quality` section (`Suggested Citation`), and the document's `license.name` and `attribution`; the later `Common Core 3` section repeats the first in other forms and adds no cadence it lacks, so it is not read. `description` is converted to plain text, then capped at 4,000 characters unless `full_description: true`; a cut one ends in `…` and carries `descriptionTruncated: true` and `descriptionLength` (the whole text's character count), and `content[]` adds a line naming `full_description: true`. Column descriptions are never shortened. `rowCount` prefers a live `count(*)`; `rowCountSource` says whether it is `live` or the `cached` fallback (see *Row totals* below).

**Error modes:**

| Error | Cause | Recovery |
|:------|:------|:---------|
| Invalid dataset ID format | ID doesn't match `[a-z0-9]{4}-[a-z0-9]{4}` | Check the ID from `cdc_discover_datasets` output -- IDs are always 9 characters like "bi63-dtpu" |
| Dataset not found (404) | Valid format but ID doesn't exist or was deleted | Search again with `cdc_discover_datasets` -- the dataset may have been replaced or retired |
| `not_queryable` | The metadata endpoint answered 200 with zero columns -- the ID names a chart, map, story, file, or external link. A chart or map names the dataset it is built on (`modifyingViewUid`), which the same document already carries | For a chart or map, call `cdc_get_dataset_schema` with the named parent; otherwise pick an ID from `cdc_discover_datasets` whose `columnCount` is above zero |
| `access_denied` (403) | Asset not readable through this endpoint, or access restricted | Permanent -- do not retry. Choose a different ID |
| Rate limited (429) | Too many requests | Retry after brief delay |
| `upstream_error` | A 5xx, an unreachable portal, no complete answer within the 20-second request deadline, or a body that is not the JSON the endpoint serves | Retry after a brief delay |

**Metadata API:** `GET https://{domain}/api/views/{datasetId}.json` where `{domain}` is `data.cdc.gov` (default) or `chronicdata.cdc.gov`.

### `cdc_list_catalog_vocabulary`

List the two controlled vocabularies `cdc_discover_datasets` matches its `category` and `tags` filters against, each value with the number of catalog entries carrying it. The filters are exact against these vocabularies (ignoring case), so a value the catalog does not carry matches nothing -- a result indistinguishable from a real value with no datasets.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `domain` | enum | No | CDC Socrata host to read from: `data.cdc.gov` (default) or `chronicdata.cdc.gov`. Both publish the same vocabulary (see *The two hosts are one catalog* below). |
| `filter` | string | No | Narrow both vocabularies to the values related to this text, matched on words in either direction (500 characters at most). A word under three letters or digits matches only an equal word, so a short filter reaches the values carrying it as a whole word. A short filter that reaches none, or one with no letters or digits, is ignored and the unfiltered vocabulary returns with a notice saying so. |
| `tag_limit` | number | No | Tags to return (default 50). No maximum: it slices a vocabulary already fetched whole, so a value at or above the tag count returns every tag. Categories are never paged. |
| `tag_offset` | number | No | Index of the first tag to return (max 10,000), for continuing a previous call. |

**Returns:** `{ domain, categories: [{ value, datasetCount }], tags: [{ value, datasetCount }] }`, both ranked by `datasetCount` descending. Enrichment carries `vocabularySize` (the unfiltered size of each vocabulary), the matched `categoryCount`/`tagCount`, and -- while tags remain -- `truncated`/`shown`/`cap`/`nextOffset` plus a `truncationCeiling` bounding the tags from `nextOffset` on. While tags remain, the paging notice offers a larger `tag_limit` as well as the next `tag_offset`.

**Vocabulary API:** `GET {catalogUrl}/domain_categories?domains={domain}` and `GET {catalogUrl}/domain_tags?domains={domain}&limit=10000`, siblings of the catalog search URL. Both answer `{ results: [{ domain_category | domain_tag, count }], resultSetSize, timings, warnings }`.

**Error modes:** the same shared `fetchJson` ladder every Socrata definition uses -- `rate_limited` (429), `access_denied` (403), `dataset_not_found` (404 from the endpoint itself), `invalid_query` (400), `upstream_error` (a 5xx, an unreachable catalog, no answer within the 20-second request deadline, or an unreadable body). The request carries only the domain and a limit, so a 400 points at `CDC_CATALOG_URL` rather than at any input. An empty result is a notice, never a failure.

### `cdc_query_dataset`

Execute a SoQL query against any CDC dataset. Supports filtering, aggregation, sorting, full-text search, and field selection. This is the workhorse -- once you know the dataset ID and column names, use this to extract data.

Accepts either a convenience `search` parameter for simple full-text queries, or individual SoQL clauses for full control. Every clause is optional: `search` serves a quick full-text query, the individual SoQL clauses give full control, and a call with none returns the first `limit` rows of every column.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `domain` | enum | No | CDC Socrata host to query: `data.cdc.gov` (default) or `chronicdata.cdc.gov`. Either returns the same rows for a given ID (see *The two hosts are one catalog* below). |
| `datasetId` | string | Yes | Four-by-four dataset identifier matching `[a-z0-9]{4}-[a-z0-9]{4}`. |
| `search` | string | No | Convenience full-text search across all text columns. Use for exploratory queries. For precise filtering, use `where` instead. |
| `select` | string | No | SoQL SELECT clause. Column names, aliases, aggregates: `"state, sum(deaths) as total_deaths"`. Omit for all columns. |
| `where` | string | No | SoQL WHERE clause. Supports `=`, `!=`, `>`, `<`, `>=`, `<=`, `AND`, `OR`, `NOT`, `IS NULL`, `IS NOT NULL`, `LIKE`, `IN(...)`, `BETWEEN`, `starts_with()`, `contains()`. Strings must be single-quoted: `"state='California' AND year=2020"`. Column names matching SoQL keywords (`group`, `select`, `where`, `order`, `limit`, `offset`, `having`, `search`) must be backtick-escaped: `` `group`='By Year' ``. |
| `group` | string | No | SoQL GROUP BY clause. Requires aggregate functions in `select`. |
| `having` | string | No | SoQL HAVING clause. Filters aggregated results. |
| `order` | string | No | SoQL ORDER BY clause. Field name with optional `ASC`/`DESC`: `"total_deaths DESC"`. For offset paging, set it from the first page, keep it for the whole walk, and end it with a per-row tie-breaker: `:id` on ungrouped rows, the grouped columns on a grouped query, the selected columns on a `distinct` select. |
| `limit` | number | No | Rows to return (default 100). One call returns at most 1,000: a `limit` from 1,001 to 1,000,000 is clamped to 1,000 and disclosed through the echoed `$limit=1000` and, when rows remain, `cap`/`truncated`/`nextOffset` and the `notice`; above 1,000,000 rejects. Up to that cap, a page comes back shorter than `limit` only at the end of the result set. Use with `offset` for pagination. |
| `offset` | number | No | Row offset for pagination. |

**Returns:** Array of row objects with requested fields. Includes `rowCount` (length of returned rows) and `effectiveQuery` — the SoQL clauses sent to Socrata as `$clause=value` pairs joined by `&`, each value in the caller's own text rather than URL-encoded, so a clause can be copied straight back into the parameter it came from. It is an echo for reading and replay, not a URL-ready string: the wire request percent-encodes these values, and `URLSearchParams` writes a space as `+` there, so decoding that encoded form is what would turn every space in a clause into a plus sign.

**Tip -- enumerating column values:** To see distinct values for a column (e.g., what states or years exist), use `select: "{column}, count(*) as count"`, `group: "{column}"`, `order: "count DESC, {column}"` (the grouped column breaks ties between equal counts, so paging over the enumeration stays gap-free). Add a `where` clause to scope the enumeration (e.g., only values where `year=2020`).

**Quirks discovered during API probing:**
- Socrata's own `$limit` default is 1000 and it sets no maximum of its own, so a page of a wide dataset is as large as its rows are wide and `select` is what narrows it. The wrapper caps a call at 1,000 rows and defaults to 100. `limit` sizes `$limit`, so the cap is a workload cap: a larger `limit` (up to 1,000,000) is clamped to it and disclosed, not rejected.
- Socrata rejects `:id` in ORDER BY once rows are grouped (`column-not-in-group-bys`), and answers it on a `distinct` select with HTTP 500.
- Response values are strings (even numbers), and geo columns are GeoJSON objects. The server relays them as returned; read each column's `dataType` from the schema.
- Year columns vary -- some datasets store year as a number, others as text. The `where` clause must match the actual type.
- Aggregate queries (`$group`) return computed columns as strings.

**Error modes:**

| Error | Cause | Recovery |
|:------|:------|:---------|
| Invalid dataset ID format | ID doesn't match `[a-z0-9]{4}-[a-z0-9]{4}` | Check the ID from `cdc_discover_datasets` output |
| Dataset not found (404) | Valid format but ID doesn't exist | Search again with `cdc_discover_datasets` |
| SoQL syntax error (400) | Malformed `where`/`select`/`group` clause -- common causes: unquoted string literals (use single quotes: `state='California'`), type mismatch (comparing text column to number or vice versa), referencing nonexistent column names | Check column names and types via `cdc_get_dataset_schema`, fix quoting, and retry |
| Type mismatch in WHERE | Comparing a text-typed year column with a number (`year=2020` vs `year='2020'`) | Inspect the column's `dataType` from schema -- use quotes for text, bare values for numbers |
| Column not in GROUP BY (400), in `select` | `select` mixes a non-aggregated column with an aggregate (e.g. `state, sum(deaths)`) without a matching `group` | Add the column to `group`, or wrap it in an aggregate like `sum()` |
| Column not in GROUP BY (400), in `order` | A grouped query orders by an ungrouped column, `:id` included. Classified by Socrata's `data.position`: the caret sits at or after the line's first top-level `ORDER BY` | Order by the grouped columns or by aggregate aliases from `select`. Never add the column to `group` -- Socrata then accepts the query and silently splits every aggregate into finer rows. Without a `position`, the `select` message applies |
| Reserved-word column name (400) | A column name matches a SoQL keyword (e.g. a column literally named `group`) and isn't escaped | Backtick-escape the column in the clause: `` `group`='By Year' `` |
| Empty results | Query is valid but no rows match the filter | Broaden the `where` clause. Use the column-values pattern above to check what values actually exist |
| `not_queryable` | Every returned row carries no fields *and* the asset's metadata reports no columns -- a `chart` or `map` ID, which the data endpoint answers 200 with a body of empty objects. The message names the dataset the asset is built on (`modifyingViewUid` in the metadata document the probe already fetched) | Permanent for this ID -- do not retry. Query the named parent dataset, or pick an ID from `cdc_discover_datasets` whose `columnCount` is above zero |
| `access_denied` (403) | ID names a `story`, `file`, or `href` asset (`no row or column access to non-tabular tables`) | Permanent -- do not retry. Confirm the ID with `cdc_get_dataset_schema`, then query one whose schema lists columns |
| Rate limited (429) | Too many requests without app token | Retry after brief delay. Use `CDC_APP_TOKEN` for higher limits |
| `upstream_error` | A 5xx, an unreachable portal, no complete answer within the 20-second request deadline, or a body that is not the JSON the endpoint serves | Retry after a brief delay. A deadline expiry on a data query is answered sooner by a narrower `where` or `select`, or a smaller `limit` |

**Query API:** `GET https://{domain}/resource/{datasetId}.json?$select=...&$where=...` where `{domain}` is `data.cdc.gov` (default) or `chronicdata.cdc.gov`.

### `cdc_query_wonder`

Query CDC WONDER for national mortality statistics — deaths, population, and crude/age-adjusted death rates — broken out by year, month, age group, sex, race, Hispanic origin, and/or underlying cause, and filtered by ICD-10 cause. WONDER is a separate CDC system from the Socrata portal the other four tools query: different host, different protocol (XML over form-urlencoded POST), no `domain` input, no dataset discovery step. Reach for it when the question is national mortality; reach for the Socrata tools when it is sub-national or not mortality.

| Parameter | Type | Required | Description |
|---|---|---|---|
| `database` | enum | No | Which mortality database to query (table below). Defaults to `underlying_1999_2020` (D76). |
| `group_by` | enum[] | No | 1–4 of `year`, `month`, `age_group`, `sex`, `race`, `hispanic_origin`, `icd_chapter`, `icd_subchapter`, `cause_113`, `leading_causes`, `injury_intent`, each at most once, in output-column order. Defaults to `["year"]`. Results are always national — location is not a grouping dimension. The last five partition deaths by underlying cause (see *Cause groupings*); `leading_causes` is accepted only on its own, and `month` rows carry deaths only. The most values the listed dimensions can take, multiplied, must be 10,000 or fewer, or the call is refused before any request; `year` beside `month`, and `icd_chapter` beside `icd_subchapter`, add nothing to the product. |
| `cause_icd10` | string \| string[] | No | ICD-10 underlying-cause code or range, or a list of up to 50 of them matched as a union — one series, one set of rates. A range must be a node of WONDER's ICD-10 tree: a chapter (`"A00-B99"`, `"V01-Y89"`), a block (`"X40-X49"`, `"C00-C97"`), or a single code (`"I21"`); any other span (`"X40-X44"`) is rejected upstream, so a code set such as the overdose definition goes in as a list. Accepted by every database. Also takes `999--999`, CDC's marker for causes withheld under the provisional database's reporting lag — that one value is accepted only on `provisional`, alone or in a list — and `999-999`, the code a sub-chapter row carries for the same stratum, which is sent as `999--999`. `""`, `[]`, or omitted means all causes; `""` inside a list is rejected, since "every cause" beside a code has no single reading. |
| `mcd_icd10` | string \| string[] | No | ICD-10 code or range, or a list of them, matched against any cause listed on the death certificate. Same form as `cause_icd10`, `999--999` included and under the same `provisional`-only restriction; the two filters AND together. Valid only on `multiple_1999_2020`, `multiple_2018_2024`, and `provisional`. Omit, or pass `""` or `[]`, for all causes — none of which counts as a multiple-cause filter, so all three pass on any database. |
| `sex` | enum | No | `all` (default), `male`, or `female`. |
| `age_groups` | enum[] | No | Age-group codes (`1`, `1-4`, `5-14`, … `85+`, `NS`; `1` is under-1-year, `NS` the group for a death whose age was not recorded). A row is included when its age group is any of the listed ones; a repeated group counts once. CDC refuses `NS` beside only some of the eleven known groups ([documented](https://wonder.cdc.gov/wonder/help/ucd.html#Not%20Stated)), so after deduplication `NS` plus 1–10 known groups fails `invalid_query` in the handler, naming the three fixes: `NS` alone, drop `NS`, or omit `age_groups`. `NS` alone and all twelve values both query. Omit (or pass `[]`) for all ages, `NS` included. |
| `year_range` | object | No | `{ from, to }`, inclusive, `from <= to` (checked in the handler). Bounds span every database (1999 → current year); the selected database's own span is enforced in the handler. Omit for all years. |
| `limit` | number | No | Rows to return from the parsed table — any positive integer. One call returns at most 10,000: a larger `limit` is lowered to that, and an omitted one takes the rest of the table from `offset` up to it. The ceiling equals the table-size bound, so one call holds any table the handler accepts. It slices a table already fetched whole, so it sizes no upstream request. |
| `offset` | number | No | Index of the first row to return, 0–10,000. Defaults to 0. |

**Returns:** `{ rows, rowCount, database, databaseTitle, caveats, cellNotes, messages, suppressedCount }`. Each row carries the requested `group_by` dimensions, then `cause_code` when grouped by `icd_chapter` or `icd_subchapter` and `cause_level` when grouped by `cause_113`, then `deaths`, `population`, `crude_rate`, and — when age standardization is possible — `age_adjusted_rate`, all rates per 100,000. Each rate is followed by its 95% confidence interval as `<rate>_lower` and `<rate>_upper` (`crude_rate_lower`, `crude_rate_upper`, and the `age_adjusted_rate` pair when the row has that rate) — CDC's own published figures, never computed here, null wherever CDC sent no interval (a `Not Applicable` rate, for one) and kept beside an `Unreliable` rate. `cause_code` is CDC's ICD-10 range for the row's node of its tree (the sub-chapter's when both are grouped), the form `cause_icd10` takes, and null where CDC sent none; `cause_level` is the row's integer depth in the 113-cause list. `database` is the selected database's dataset code (`D76`, `D176`, …) and `databaseTitle` CDC's own title for it, so a result names its own source rather than needing one looked up. `caveats` holds CDC's own footnotes for the result set. `effectiveQuery` echoes the database, grouping, and filters as a readable summary, and `totalCount` the rows in the whole table; a bounded page adds `truncated`/`shown`/`cap` and a `nextOffset`. `cap` is the `limit` that ended the page, and appears only while rows remain past it.

#### Row pagination

A four-dimension grouping is a legitimate epidemiological query and a large table: 22 years × 12 age groups × 2 sexes × 4 bridged race groups is ~2,100 combinations on `D76` before CDC hides the zero-death and suppressed-death rows. A `["year","age_group","sex","race"]` run on `D76` returns 2,014 rows. `limit` and `offset` page it, keeping the field names and semantics `cdc_query_dataset` and `cdc_get_dataset_schema` use.

**Decision: the page is taken from the parsed table, not asked of CDC.** WONDER's request XML has no offset or limit equivalent (`xml-builder.ts` sends the whole grouping), so the upstream request stays singular and the table arrives whole either way. Two things follow. `totalCount` is exact and free — unlike `cdc_query_dataset`, where the SODA endpoint reports no total and continuation is an over-fetch probe. And a page is a pure view: every row CDC sent is reachable at some offset, and the query does not change between pages, so a caller who needs the complete table follows `nextOffset` rather than narrowing `year_range` into a different question.

**Decision: `limit` is the page, lowered to a 10,000-row per-call ceiling; omitting it takes the rest of the table up to that ceiling.** A page that ends short of the `limit` the caller set, at a point that depends on row width, leaves `cap` naming a size the page never reached and the caller unable to plan a walk. WONDER's request carries no limit of its own, so every call re-runs the whole query behind the 16-second gap and repeats the caveats and messages: a small default would multiply both, and a smaller `limit` saves no time. The ceiling equals `WONDER_MAX_TABLE_ROWS`, the most rows a grouping may be able to produce (next decision), so every table the handler accepts fits one call. A page that stops short of the end sets `truncated`, `shown`, `cap`, and `nextOffset = offset + shown`; `totalCount` stays exact, and the notice gives the row span and the `offset` to continue from.

**Decision: a grouping whose table could pass 10,000 rows is refused before any request.** Each dimension has a ceiling on the values it can take — `year` the years queried, `month` twelve per year, `age_group` the groups selected, `sex` one or two, `race` four on the bridged databases and seven on the single-race ones, `hispanic_origin` three, and for the cause groupings the values in CDC's lists (20 chapters, 177 sub-chapters, 137 causes in the 113-cause list, 15 leading causes, 6 injury intents, plus one withheld-cause row on the provisional database for chapter and the 113-cause list). Their product bounds the table, except that a coarser level grouped beside its finer one counts 1: a `month` cell is a year-month and a sub-chapter lies inside one chapter, so the finer level already enumerates the coarser, and `["year","month","sex"]` on `D76` bounds at 528 rows, not 11,616. Past 10,000 rows WONDER takes longer than the 20-second request deadline to answer, a failure that reads as retryable and that no retry fixes. The handler fails `invalid_query` naming the product and the dimensions, before the request, in the same shape as the other relational checks. `year_range`, `sex`, and `age_groups` narrow the product; a cause filter does not, since how many causes of a grouping it covers is not known before CDC answers. Every count is a ceiling, since CDC hides strata with no deaths. WONDER's own limit of 75,000 rows sits far past what it answers inside the deadline, so the bound is the deadline's, not WONDER's.

`offset` defaults to 0 and an offset at or past the row total returns an empty page with a notice, not an `invalid_query` — a spent offset is a finished walk, not a malformed request, and reporting it as an error would be indistinguishable from a query that matched nothing.

**Decision: `cellNotes` is re-scoped to the page; `caveats` and `messages` are not.** The parser numbers a cell note against the whole parsed table, and `format()` looks a token up by the index of the row it is rendering. A page carrying the table's numbering therefore paints `Suppressed` and `Unreliable` markers onto whichever rows happen to sit at those indices — silently, from the second page on, and onto public-health figures where a withheld value and a published one are not interchangeable. So the notes are filtered to the rows returned and re-based onto them, and `suppressedCount` is recounted from the page. `caveats` and `messages` go the other way: both describe the table CDC assembled, and the hidden-row notices in particular are the only evidence that whole strata were dropped, so scoping them to a page would let that disclosure vanish from the page a reader stops on.

`year` (`.V1-level1`), `age_group` (`.V5`), `sex` (`.V7`) and the underlying-cause finder (`.V2`) carry the same variable code on all five, and their option lists match too apart from two `D176` details *Fidelity to CDC's own vocabularies* covers — the `999--999` marker its cause finders add, and the *All Genders* wording on its `.V7` all-values option. **`race` is the only dimension that genuinely diverges**, and it diverges in meaning as well as code: bridged race collapses Asian and Pacific Islander into one group, single race splits them and adds a multiracial category. A race series from one family cannot be spliced onto one from the other, which is why both the `database` and `group_by` descriptions say so.

The provisional database is a multiple-cause form that also carries the full underlying-cause variable set, so a provisional *underlying-cause* query is `D176` with `cause_icd10` — there is no separate provisional underlying-cause database. Its year cells come back as CDC's own labels (`2025 (provisional)`, `2026 (provisional and partial)`), not bare years, which is why nothing downstream parses a year out of a dimension cell.

**Decision: the provisional database's reporting lag is disclosed from the years queried, not from the labels returned.** Two clauses, both written into `notice` whenever they apply. First, the database's latest year holds deaths only through a data-through date, which the response states in its `<dataset>` vintage (`vintage="October 17, 2026 as of  October 25, 2026"`; the final databases send a bare year there, which names no date), while its population is the full-year estimate, so counts and rates for that year read low and compare with no finished year. A year grouping shows the `(provisional and partial)` label, but a `["sex"]` grouping sums the partial year with no label in sight, so the clause keys on `year_range`, or every year the database holds, reaching the data-through year. A `month` grouping carries the same `(provisional and partial)` label on every recent month, so the clause also names the month the data-through date falls in as partial — October 2026 held 105,025 deaths through the 17th against September's 234,461 — unless the date is that month's last day. Second, CDC withholds the cause of external-cause (V01-Y89), sudden-death (R95, R96) and, on the multiple-cause finder, drug-poisoning (T36-T50) deaths for the 24 weeks before the data-through date and counts them under `999--999` until their cause is released, so a cause filter that reaches one of those spans — a block or chapter containing one counts — undercounts those weeks, as does a cause grouping with no underlying-cause filter keeping it clear of them, whose withheld deaths fill a row of their own. The clause points at `cause_icd10` `999--999` for the withheld count and says that count spans every withheld cause at once, so it bounds what one filter or cause row is missing and is never added to it. The window is checked on its own, since a data-through date in January opens it in the year before. With neither a cause filter nor a cause grouping there is no second clause: CDC counts the withheld deaths in all-cause totals. A response that names no data-through date still gets both clauses, keyed on the database's last year and worded without dates.

#### Cause groupings, Hispanic origin, and month

`icd_chapter` (`.V2-level1`), `icd_subchapter` (`.V2-level2`), `cause_113` (`.V4`), `leading_causes` (`.V28`), `injury_intent` (`.V22`), `hispanic_origin` (`.V17`), and `month` (`.V1-level2`, the second level of the date variable `year` is the first of) carry the same variable code on all five databases, and WONDER attaches the full population and both rates to every cause row, as to any other stratum. Chapter and sub-chapter cells name their node of CDC's ICD-10 tree in a `cd` attribute, which becomes `cause_code` in the form `cause_icd10` takes, so a row chains straight into a filter; `cause_113` cells give their depth in the nested list as `h`, which becomes `cause_level`. The other cause groupings send neither, and the codes some labels quote (`#Tuberculosis (A16-A19)`) stay label text. Three consequences are handled in the tool, not left to the caller:

- `cause_113` rows nest — a cause below level 1 is part of the cause one level up — so deaths do not sum across levels, and the notice says so.
- WONDER refuses `leading_causes` beside any other grouping with HTTP 500 (`The 15 Leading Causes lists can't be combined with any other Group By variables.`), so the handler fails `invalid_query` before the request. The cause filters still apply: with `cause_icd10: "V01-Y89"` it ranks the rankable causes inside that range. `cause_113` holds the same causes, marked `#`, and combines with other dimensions.
- CDC publishes no monthly population, so `month` rows carry deaths only and population and both rates come back `Not Applicable`.

**Decision: cause of death is both a filter and a grouping.** WONDER returns a population and both rates on a cause-partitioned row, on every database, so nothing bars grouping by cause. "What were the leading causes of death?" and a comparison across causes are first-stop mortality questions that one filtered call per cause answers poorly — each call costs a 16-second gap, and a ranking needs every cause up front — and Hispanic origin and month have no filter to fall back on. The age-adjusted rate follows its usual rule: dropped only when `age_group` is grouped or one age group is selected.

#### Fidelity to CDC's own vocabularies

Two questions run through the request builder and the response parser, and they are the same question from either side: does a value the tool hands back read the way CDC wrote it, and can an input express everything the database's own form offers? The line below is where both are drawn. Each `V_*` option list was read off the five request forms.

**Decision: a variable becomes a `group_by` dimension when WONDER answers it with the full measures and it settles a first-stop mortality question; every other variable stays absent.** `.V4`, `.V28`, `.V22`, `.V17`, and the second levels of `.V2` and `.V1` meet that bar (see *Cause groupings, Hispanic origin, and month*). The rest are each a whole dimension rather than a value missing from one the tool already has, so each needs its own input, its own vocabulary in a `.describe()`, and its own answer to how it interacts with `group_by` — a different piece of work from making an existing input faithful, and a wider tool than the surface `group_by` describes. The remaining grouped-cause taxonomies are the clearest case: `GR130-001` and `D1` are identifiers in a second cause vocabulary, not codes `cause_icd10` could take, and `cause_113` groups by the 113-cause list without offering a filter in it. The request builder submits every variable it does not expose at `*All*`, because WONDER validates the variable block as a whole.

**Decision: `999--999` ships as a value on both cause inputs.** CDC lists it in `D176`'s two ICD-10 finders for deaths whose cause it is still withholding under the provisional database's six-month reporting lag — a real and sizeable stratum (2026, as any listed cause: 123,612 deaths). It is not an ICD-10 code and cannot be written in the shared pattern, so it is accepted as its own literal. The databases whose finders do not list it answer HTTP 500 with `Invalid 'ICD-10 Codes' codes were found: '999--999'. Check the Finder Tool for valid ICD-10 Codes codes.` — correct, but it reads as "no such code" when the code is real and sitting on another database, so the handler rejects that combination first and names `provisional`, in the same shape as the `mcd_icd10` and `year_range` checks. The check tests list membership, so the marker is caught inside a list too. On a cause grouping the same stratum appears as a row of its own inside the withholding window — `999--999` by chapter, `999-999` by sub-chapter — which is why the lag notice names it. Both cause inputs take `999-999` too, so a sub-chapter row chains into a filter like any other, and send it as `999--999`: WONDER accepting `999-999` as a finder value is unverified, so that form never reaches the wire.

**Decision: both cause inputs take one value or a list.** Standard cause-of-death definitions are code sets: CDC's drug-overdose definition is X40–X44, X60–X64, X85 and Y10–Y14, and firearm and suicide deaths have the same shape. WONDER's finder accepts only nodes of its ICD-10 tree — `X40-X49` is a block and returns data, `X40-X44` is a span and draws `Invalid 'ICD-10 Codes' codes were found: 'X40-X44'` — but it ORs any number of `<value>`s on one finder into a single series, and ANDs the `.V2` and `.V13` finders. So each list entry becomes one `F_<ID>.V2` (or `.V13`) value, the shape `year_range` already uses for `.V1`, and `I_` carries the codes space-joined as the form submits it. Verified against `D76` (X40–X44 by year: 2018 58,908, 2019 62,172) and `D77` (overdose set AND T40.0–T40.4, T40.6, 2019: 49,860). The input is `string | string[]` rather than array-only so every existing string call stays valid; one call per code was never an alternative, since counts can be summed afterwards but crude and age-adjusted rates cannot. Repeated entries are dropped, since the OR makes them redundant.

**Decision: a cause list holds at most 50 entries.** WONDER publishes no cap on finder values, and the longest list verified upstream is the 16-code overdose set. Fifty spells out any of CDC's standard code-set definitions code by code (the firearm set is 13), while a block or chapter covers anything wider in one entry. The bound is structural, so it lives on the schema as `maxItems`, where a client sees it before calling.

**Decision: dimension labels are trimmed at the edges and left alone everywhere else.** `D158` and `D157` render their last year as `2024 `; every other year on every database, `D176`'s own 2024 included, comes back bare. Untrimmed, `"2024 " !== "2024"` splits one year into two keys the moment a caller lines a row from one database up against the same year from another, and nothing in the output marks the padded cell as different from the bare one beside it. Whitespace at the edge of a label carries no meaning, so `dimensionLabel` drops it once in the parser rather than leaving every consumer to find it. Nothing inside a label moves: `2025 (provisional)` keeps its interior space, and the age and race labels keep CDC's own wording (`< 1 year`, `More than one race`).

**Two labels the tool never has to reconcile.** `D176` calls its `.V7` all-values option *All Genders* where the other four say *All*; the tool never surfaces that label, since a `*All*` selection means no sex breakdown and a sex grouping returns `Female`/`Male` on every database. And the single-race `.V42` list carries a `Not Available` group — the race analogue of the age `NS` — which can appear as a `race` dimension value; it is CDC's own label and passes through as written.

**IDs are pinned, not resolved per call.** `GET /controller/datarequest/<ID>` returns a plain message page naming the request page an ID belongs to, and a retired or never-allocated ID names none — an unambiguous check that spends no rate-limited POST. `tests/services/wonder/database-ids.test.ts` runs it under `WONDER_LIVE_TESTS=1`, leaving the default test run hermetic. WONDER does mint a new ID per vintage for its archived datasets (cancer runs D144/D151/D160/D172, TB runs D147/D156/D165), so the mortality IDs surviving vintages is the exception rather than the rule and is worth re-checking rather than trusting forever.

**Decision: one tool with a `database` enum, not a tool per database.** The engine, throttle, response parser, error classification and roughly 90% of the parameter scaffold are shared, and the axis that varies is a single enum value. Separate tools would triple a surface to express one dimension, and would leave a caller who wants "the same query, current years" re-reading a second tool's schema to find it unchanged. The divergences that do exist — race vocabulary, year span, whether `mcd_icd10` applies — are per-database facts, so they live in `.describe()` and in a handler validation.

**Decision: each database's fixed-parameter block is built from its own request form.** `POST /controller/datarequest/<ID>` with `stage=about&action-I Agree=I Agree` returns the form; `SCAFFOLDS` in `xml-builder.ts` is transcribed from it. Templating `D76`'s block and swapping the prefix returns HTTP 500 — `The second box of the AND combination for '{0}' contains an entry while the first one is empty` (WONDER leaves the `{0}` unexpanded, so the message does not name the variable). The scaffolds differ structurally, not just in codes: the multiple-cause finders run in `fadv` mode with paired `V_*.V13`/`V_*.V13_AND` textareas D76 has no analogue for, and `D176` carries occurrence-location (`V77`/`V79`/`V80`/`V81`/`V89`/`V90`/`V91`), MMWR-week (`V100`) and 2023-urbanization (`V18`/`V82`) variables D76 lacks while omitting D76's weekday variable (`V24`).

**Decision: the multiple-cause databases ship only together with `mcd_icd10`.** Grouped by year with no multiple-cause filter, `D77` returns `D76`'s figures to the digit — each death is still counted once, by its underlying cause. Offering the database without the filter would be surface area for a no-op. With the filter it answers a question no underlying-cause query can: `D77` filtered to `J00-J98` as any listed cause returns 746,954 deaths for 2019 and 1,031,759 for 2020, against ~2.85 M and ~3.38 M all-cause — the "died with a respiratory condition recorded anywhere on the certificate" population. Selecting a multiple-cause database without the filter is met with a notice naming the underlying-cause database that returns the same numbers. `provisional` is exempt from that notice: its years run past where the final databases stop, so selecting it is never a no-op.

**Decision: the per-database year span is enforced in the handler, not the schema.** `year_range`'s bounds are the union of every database's span, so the emitted JSON Schema stays a plain numeric range a client can read. The cross-field check deliberately avoids a Zod `refine`/`superRefine`: a refinement contributes nothing to the emitted schema, so a client never sees the constraint, and a schema rejection fails argument parsing as `-32602` `invalid_arguments` before the handler runs — which puts the declared `invalid_query` reason and its `recovery` hint out of reach. The same rule holds for `cdc_discover_datasets`. The handler check fails with the declared `invalid_query` reason and a message naming the selected database's actual span; the `mcd_icd10` and `999--999` rejections follow the same pattern.

**Decision: every relational input check settles in the handler, before any request.** A reversed `year_range` (`from` later than `to`) and a `group_by` listing one dimension twice both fail `invalid_query` naming the input at fault; left to WONDER, the repeated dimension spends a rate-limited request to draw `Group Results By values have duplicates`. Inputs that are unions are deduplicated instead of rejected, in one normalization step that runs before anything reads them: `age_groups` and both cause lists. For `age_groups` it is load-bearing — `["25-34","25-34"]` otherwise reads as two groups on both sides, so this server keeps `age_adjusted_rate` and WONDER computes it, returning the crude rate under the age-adjusted name. A repeated `group_by` dimension is rejected rather than dropped, because the list sets the output columns and silently removing one changes the table the caller asked for. `NS` beside only some of the known age groups is checked on the deduplicated list, so `["NS","NS"]` still reads as `NS` alone; left to WONDER it spends a rate-limited request on every database to draw `The 'Not Stated' Age value cannot be combined with other values`, whose recovery hint points at the wrong inputs.

**Age-adjusted rate is not a measure code.** `O_aar=aar_std` produces the column; no mortality database defines an `M4`, `D76` included — a `D76` request carrying `O_aar=aar_std` and no `M_4` returns the age-adjusted column normally (1999: deaths 2,391,399 · population 279,040,168 · crude 857.0 · age-adjusted 875.6). The measure codes sent are `M_1..M_3` (deaths, population, crude rate) and `M_32`.

**Decision: both rates' 95% confidence intervals are requested explicitly, on every database.** `M_32` (`<ID>.M32`) asks for the crude rate's interval and `O_aar_CI=true` for the age-adjusted rate's, sent whenever that rate is requested. `D158`, `D157`, and `D176` return both intervals either way, while `D76` and `D77` return none without them (`M_32` alone adds only the crude one), so relying on per-database defaults would give one request shape two answers. Neither adds a cell: CDC nests each interval inside its rate's cell as an `<l v="(lower - upper)"/>` child, which the parser reads into `<rate>_lower` and `<rate>_upper`. The bounds are CDC's published figures. Computing intervals locally was rejected, since it cannot reproduce WONDER's age-adjusted ones; a nested `{ lower, upper }` object per rate was rejected, since rows are flat, column-keyed records that `format()` and `cellNotes` both read by column name. The intervals are often the only stability signal: the 2018-on databases publish a rate from a handful of deaths as a number where `D76` and `D77` return `Unreliable`.

**Age-adjusted rate is conditional.** It is requested only when WONDER can standardize across age, which rules out the two shapes it rejects: `age_group` used as a grouping dimension (age is then the output axis, not the standardization axis), and an `age_groups` filter narrowed to exactly one group. In both cases the column is simply absent from every row rather than null.

**Status tokens in place of numbers.** A measure cell can come back as `Suppressed` (withheld for confidentiality — figures representing fewer than 10 persons), `Unreliable` (a rate CDC judges statistically unstable and shows as the token in place of the rate), or `Not Applicable` (no population denominator). The parser nulls the cell in `rows` and records it in `cellNotes` as `{ row, column, token }`; `suppressedCount` counts the `Suppressed` ones. `rows` alone cannot tell a withheld value from an unreliable one or a genuinely absent one — `cellNotes` is what does.

**`Unreliable` is a per-database criterion.** CDC states the rule in the caveat it attaches to each result, and `WONDER_DATABASE_SPECS` carries it as `unreliableCriterion`, so the tool and token text cannot drift from it. `D76` and `D77` flag a rate computed from 20 or fewer deaths ("a numerator of 20 or less"). `D158`, `D157`, and `D176` flag a rate whose 95% confidence interval is wider than 160% of it, whatever the death count — they publish some rates from a handful of deaths as numbers and flag others on much larger counts. On every database the token replaces the rate, and the row's deaths and population stand. An `Unreliable` rate keeps the confidence interval CDC published with it.

**Hidden rows, and why they need their own disclosure.** A status token marks a cell WONDER withheld inside a row that still arrived. WONDER also drops rows outright before sending the table: `suppress-zeros` and `suppress-counts` are on for every mortality database, so a stratum with zero deaths and a stratum whose death count falls under the suppression threshold never appear at all. Nothing in the table records the omission — the surviving rows simply read as the whole answer, and a caller cannot separate "this stratum has no deaths" from "this stratum was dropped." WONDER states it instead in `<message>` elements on the 200: `Rows with zero Deaths are hidden.` and `Rows with suppressed Deaths are hidden.`, alongside unrelated notices such as the one about totals being unavailable under suppression constraints. `parseMessages` reads all of them and `messages` carries them verbatim; the handler turns the hidden-row ones into a notice, and `format()` renders the block under the table so a `content[]`-only client sees it too.

**The notice keys on which message CDC sent.** `hiddenRowsKind` reads each message as `zero_deaths`, `suppressed_deaths`, or `unspecified` (a hidden-rows message naming neither, read the cautious way, as suppression); a message with several such sentences takes the most cautious kind among them. A stratum hidden for zero deaths recorded none, so with that message alone the deaths summed from `rows` are complete, only population leaves those strata out, and an empty table says CDC recorded no deaths for the combination, with no advice to widen the query. The suppressed-deaths message, alone or beside the other, means a stratum missing from `rows` may have been dropped rather than unobserved, so counts, rankings, and completeness claims drawn from `rows` are partial, and an empty table is not evidence that nothing matched — every matching stratum can be hidden, which reads as zero rows and means the opposite.

**Decision: an empty page renders no cause.** `format()` sees only the page, and a page past the end of the table looks exactly like a query that matched nothing, so its empty branch is the `**<database> — <title> — 0 rows**` heading alone, followed by the CDC-notices and caveats blocks as on any page. The cause reaches `content[]` once, through the notice the handler writes from `totalCount` and `offset`: "No rows matched …" for an empty table, "CDC recorded no deaths for this combination" when its only hidden-row message is the zero-deaths one, the withheld-rows wording when CDC also reported suppressing rows, and "offset N is past the end of this table …" for an exhausted page — the shape `cdc_query_dataset` uses.

**Decision: disclose the hidden rows, don't unhide them.** `fixedParams()` deliberately omits `O_show_zeros` and `O_show_suppressed`. Sending them would return the dropped rows, but it changes the result set materially rather than adding a field: every zero and sub-threshold stratum enters the table, and the suppressed ones arrive as rows whose measures are all `Suppressed` status tokens — the per-cell disclosure the parser already carries. That is a defensible design, and a bigger one than a disclosure: it needs its own pass over row-count growth at fine groupings, over how a fully-tokenized row should render, and over whether it belongs behind an input. Disclosure answers the question that was actually wrong (the caller not knowing) without moving the data contract, so it ships first and unhiding stays open.

**Upstream constraints encoded in the request builder:**

- **National only.** Sub-national grouping and filtering are blocked by CDC vital-statistics policy, so location (`.V9`/`.V10`/`.V27`, plus the occurrence-location finders on `D176`) is pinned to `*All*` and never exposed as an input.
- **Every request must carry a rate measure.** A deaths-only measure set is rejected by the WONDER engine, so deaths, population, and crude rate are always requested.
- **A year filter must be set on the finder as well as the value.** Listing specific years in `V_<ID>.V1` while leaving `F_<ID>.V1` at `*All*` is rejected as a conflicting selection, so both carry the year list.
- **An honest `User-Agent`, and nothing else browser-like.** WONDER sits behind a bot filter that rejects browser-*claiming* clients — a browser User-Agent plus Origin/Referer with a non-browser TLS fingerprint draws a 403 — and answers Node's default `fetch` client string with the same 403 while it serves Bun's and curl's. Requests carry a `Content-Type` and a `User-Agent` naming this server and its repository (`USER_AGENT`, shared with the Socrata service so neither upstream depends on a runtime's default client string), so the call behaves the same on both runtimes.
- **One request per 16 seconds, measured from the end of the previous response.** WONDER documents 15 s, but the window is not anchored on the previous request: a request sent 15.01 s after the previous one *started* (14.11 s after its response) is rejected, while 15.21 s after the response is accepted. The service therefore stamps the clock after it has read the response body — on every exit path, since a network error, a 429, and a malformed body all consumed a request — and waits 16 s from there, leaving margin for clock skew and upstream jitter. The 429 carries no `Retry-After` and does not lengthen the window, so a fixed interval is enough; there is no backoff state. The limit is per source IP and shared across databases, so one process-wide gap is the correct shape.
- **A 20-second deadline per request, over the response headers and body.** The lane is process-wide, so one request that never answers would hold every later call, across all sessions on a hosted process. The clock is an `AbortController` fired by `setTimeout` and cleared in `send()`'s `finally`, composed with the caller's signal through `AbortSignal.any`. It is not `fetchWithTimeout`, whose status-mapped non-2xx errors would replace this service's own `<message>` → `invalid_query` and 429 → `rate_limited` classification, nor `AbortSignal.timeout()`, which the framework avoids under Bun and fake timers cannot drive. Expiry is the retryable `upstream_error` and releases the lane, and the next call still waits 16 seconds from it; a caller's abort, queued or in flight, surfaces as the caller's cancellation, never as an upstream failure. A 429 is answered from its status before its body is read, so a refusal whose body stalls cannot hold the lane until the deadline and then read as retry-now. The deadline covers neither the wait for the lane nor the gap, so a call queued behind one stalled request settles within 20 + 16 + 20 = 56 seconds, inside the 60-second default request timeout of MCP SDK clients.

- **Decision: overlapping calls queue in one lane.** A stamp read on entry is not enough when calls overlap: calls that arrive together read the same stamp, wait the same time, and send in the same instant, so all but one draw a 429. `query()` therefore chains each call on the previous call's settlement before it measures the gap — settlement rather than success, so a failed or aborted call never wedges the calls behind it. A call aborted while it waits rejects at once and sends nothing; its lane slot still resolves only after the call ahead of it, so the next call keeps waiting for the request actually in flight, and only a sent request stamps the clock. The lane is process-wide like the gap, never per database. The k-th queued call returns after roughly k × (16 s + response time), which the tool description states.

**Error modes:**

| Error | Cause | Recovery |
|:------|:------|:---------|
| `invalid_query` | A reversed `year_range`, a repeated `group_by` dimension, `leading_causes` beside another `group_by` value, a grouping whose dimensions could make a table of more than 10,000 rows, `age_groups` holding `NS` beside only some of the known groups, a `year_range` outside the selected database's span, `mcd_icd10` against a database that records only the underlying cause, or `999--999` against one that keeps no withheld-cause backlog — all rejected in the handler before any request is sent. Or WONDER itself answered with a `<message>`: an ICD-10 code or range its tree does not hold, or a filter/grouping combination it forbids | Read the returned message — it names the input at fault, the span the selected database holds, the databases that accept `mcd_icd10` or `999--999`, the row count a grouping could reach, or the part WONDER rejected. Fix `year_range`, `group_by`, or `age_groups`, narrow the grouping or its filters, switch `database`, drop the filter, or correct the ICD-10 code, and retry |
| `rate_limited` (429) | A request reached WONDER less than 15 seconds after the previous response to the same source IP finished — usually another client on that IP, since this server queues its own calls | Wait at least 16 seconds after the previous response completes, then retry; concurrent retries queue and run one at a time, each adding about 16 seconds |
| `upstream_error` | Unreachable, no complete answer within the 20-second request deadline, a failure with no `<message>` to explain it, or a 200 carrying no `<data-table>` | Retry after a brief delay; wonder.cdc.gov may be temporarily unavailable |
| Empty results | Valid query, no matching deaths — CDC recorded none when its only hidden-row message is the zero-deaths one — or every matching row suppressed upstream, which `messages` distinguishes — or an `offset` past the end of the table, which `totalCount` distinguishes. The notice names which | Broaden `cause_icd10`, `sex`, `age_groups`, or `year_range`, or confirm the ICD-10 code covers the years selected; for a spent offset, lower `offset` below `totalCount` |

**WONDER API:** `POST https://wonder.cdc.gov/controller/datarequest/<ID>` where `<ID>` is the selected database's dataset code, form-urlencoded with a `request_xml` document; the response is an XML `<data-table>`. Not configurable — unlike Socrata, there is no second host.

**Not covered:** natality, compressed-mortality, cancer, and STD databases. Each is its own WONDER dataset with its own measures and variables, not a `database` value away.

## Resources

### `cdc://datasets`

The catalog's 50 most-viewed entries, each as `{ id, name, assetType, category, columnCount, updatedAt }`, for orientation in the CDC data landscape.

It reads the same catalog as `cdc_discover_datasets` and returns the same mix of asset types — the live top 50 carries two charts, a story, and two `filter` entries alongside the datasets. `columnCount` is what separates them: an entry reporting 0 is not tabular, and neither `cdc_get_dataset_schema` nor `cdc_query_dataset` returns anything for its ID.

**Pagination:** the underlying Discovery API takes `limit`/`offset` (`GET https://api.us.socrata.com/api/catalog/v1?domains=data.cdc.gov&limit=50&offset=0`); this resource pins them at 50 and 0 and accepts no caller input. `totalCount` (~1,480 entries) comes back with the page — use `cdc_discover_datasets` to page past the first 50.

### `cdc://datasets/{datasetId}`

Dataset metadata and schema, addressable by URI. The same failures as `cdc_get_dataset_schema` — including `not_queryable` when the ID names a catalog asset with no columns, which names the parent dataset of a chart or map — and its default-call payload: the first 100 columns and a description capped at 4,000 characters, with the same `parentId` and publisher provenance fields. It takes no selector, so the whole description and later column windows come from `cdc_get_dataset_schema` (`full_description: true`, `column_offset`); one `notice` names both when both apply. `datasetId` must match `[a-z0-9]{4}-[a-z0-9]{4}`.

### `analyze_health_trend`

Structured workflow for investigating a public health question across CDC data. Opens by settling which of the two systems answers the question — `cdc_query_wonder` when it is national mortality with an ICD-10-expressible cause or a question that ranks or splits causes (leading causes, Hispanic origin, and seasonal month questions included), the Socrata trio for sub-national detail and non-mortality topics — then guides the agent through: (1) discover relevant datasets, passing over a `columnCount` of 0 and following a chart or map to the dataset its `parentIds` name, (2) inspect schemas, (3) query for baseline data, (4) compare across time/geography/demographics, rates by their 95% confidence intervals, (5) synthesize findings with caveats about data limitations: whether the dataset is still updated (`updateFrequency` and `temporalCoverage` beside `updatedAt`) and, for the provisional database, its partial latest year. Steps 1 and 2 branch by source: the WONDER path has nothing to discover and a fixed shape, so it goes straight to the baseline query.

The routing is prose the reading model acts on, not a classification the handler performs — the generated message is identical whatever `topic` says. A topic keyword test in `generate` would fail exactly where the question is ambiguous, and would need re-tuning every time either system's coverage moves; stating the conditions leaves that judgment with the reader, who has the full question. `tests/mcp-server/prompts/definitions/analyze-health-trend.prompt.test.ts` holds the text to the tool surface: every backticked identifier must resolve to a real tool name, field, or enum member, and the year span the WONDER guidance advertises is read off `cdc_query_wonder`'s own input schema rather than hard-coded.

## Implementation Notes

- **The two hosts are one catalog** -- `data.cdc.gov` and `chronicdata.cdc.gov` are two front doors onto a single Socrata tenant, so `domain` chooses which host answers, not which assets are reachable. Measured against the live API: `?domains=chronicdata.cdc.gov` and `?domains=data.cdc.gov` both return ~1,480 entries, same IDs in the same order, every result labelled `metadata.domain: data.cdc.gov`; `swc5-untb` (PLACES county) and `bi63-dtpu` (a `data.cdc.gov`-native dataset) each answer 200 on both hosts; `q=PLACES` against the default host returns 109 results including the 2025 place, county, and GIS-friendly releases. The `domains=` parameter is honored in general -- `domains=data.cityofnewyork.us` returns a distinct 3,014-entry catalog -- it is only this pair of CDC hosts that shares a tenant.

  **Decision:** keep the input, describe it accurately. It is load-bearing for the SSRF allowlist and for callers that pin a host, and dropping it would break them for no gain; but no surface may name PLACES, the Heart Disease & Stroke Atlas, or Environmental Public Health Tracking as though selecting `chronicdata.cdc.gov` were the way to reach them. `tests/services/socrata/socrata-domain-semantics.test.ts` pins the described behavior so the claim cannot drift back.

- **Authentication** -- No API key required. Optional app token via `X-App-Token` header increases rate limits. Without a token, requests are throttled by source IP (undocumented exact limits, but functional for moderate use).
- **Rate limits** -- Unauthenticated requests are throttled (no published rate). With an app token, limits are higher. The SODA API returns no rate-limit headers -- implement conservative request spacing (200-500ms between requests).
- **Response types** -- SODA v2.1 JSON values are strings, numbers and dates included, and geo columns are GeoJSON objects. Read each column's type from the schema endpoint's metadata.
- **Dataset staleness** -- Some datasets are marked as no longer updated (particularly COVID-era datasets). The `data_updated_at` field from the catalog/metadata API says when the data last changed (`updatedAt`), and `updateFrequency` and `temporalCoverage` on the schema surfaces say whether the series is still maintained and what period it covers. Surface these to the agent.
- **Suppressed values** -- Some health datasets suppress small counts for privacy. These appear as missing values or footnote markers rather than zeros. Surface footnote columns when present.
- **Large result sets** -- Default limit is 100 rows; one call returns at most 1,000. `cdc_query_dataset` reports no total for a *result set*: the SODA data endpoint reports none, and buying one per query with a `$select=count(*)` round trip was rejected on latency grounds — a count of the filtered rows would have to be re-bought on every page. Continuation is established instead by an **over-fetch probe** -- `SocrataService.query` asks the wire for `limit + 1` rows, drops the extra, and returns `hasMore`. That separates a last page which happens to fill the limit exactly from one that was cut short, which a `rowCount === limit` test cannot; the echoed `query` keeps the caller's own `$limit` so it stays replayable. Socrata's parse errors quote the query it compiled, which ends `limit <limit + 1> offset <n>`; the service swaps that tail back to the caller's `limit` in every copy the message quotes before relaying it, so the probe is out of everything the caller sees -- an unexpected-character error quotes the query twice, inline and again above a caret line. Every caller clause precedes the tail, so a `character N` position and that caret still point at the same character.

  **Decision: `limit` is the page, with a 1,000-row per-call ceiling and no character budget.** SODA sets no maximum of its own, so how large a page of a wide dataset is depends on how wide its rows are, and `select` is the caller's lever on it. A character budget would end a page short of `limit` at a point that depends on row width, leaving `cap` naming a size the page never reached and the caller unable to plan a walk, so the ceiling is the one bound and, up to it, a page comes back shorter than `limit` only at the end of the result set. The caller sees the same rows on both surfaces: `structuredContent` and the rendered table in `content[]`.

  **Decision:** bound the call, not the input range. `MAX_LIMIT` is 1,000 per call and the offset ceiling is 1,000,000 -- rejecting a `limit` past 1,000 would break callers over a problem a clamp settles. A `limit` past 1,000 has one obvious reading, so it is clamped rather than rejected: `limit` accepts up to 1,000,000 (past which no offset reaches), the request and the `$limit` echo carry 1,000, `cap` reports 1,000, and the continuation notice names the clamp when rows remain. The tool discloses `truncated`/`shown`/`cap` plus a `nextOffset` that resumes exactly where the page stopped. `nextOffset` is withheld when resuming would exceed the offset ceiling, since a value the caller cannot replay is worse than none.

  **Decision: the resume advice orders by a tie-breaker the query's shape admits, appended to the caller's own `order`.** Offset paging over SODA needs a deterministic `order` -- results are not implicitly ordered -- but `:id`, the system field on every dataset, is only valid on raw rows: Socrata rejects it once rows are grouped and answers it with HTTP 500 on a `distinct` select. Advising `:id` everywhere would send grouped callers into a `column-not-in-group-bys` error, and adding `:id` to `group` to clear it splits every aggregate into per-row values. The notice keeps the caller's order as written and appends the grouped columns on a grouped query (`order="total DESC, state"`), the selected columns (by alias when they have one) on a `distinct` select, and `:id` on raw rows (`order="year DESC, :id"`); a tie-breaker the order already carries is not repeated. The lists are split at top-level commas only -- never inside parentheses or a quoted literal or identifier -- in one linear pass. The request's own `order` is never rewritten.

  **Decision: when the advice adds a tie-breaker, the walk restarts at offset 0.** A page read under an order with ties, or with no order, is not a prefix of the tie-broken order: ties come back in no fixed sequence, so continuing at `nextOffset` under the suggested order skips some rows and repeats others. Measured live on `bi63-dtpu` grouped by `state` under `n DESC`, page one was Texas, Oregon, Idaho, Alaska, Alabama, and offset 5 under `n DESC, state` began at Colorado -- Arizona, Arkansas and California never came back, and the first page's rows returned later. So when the order already carries the tie-breaker the notice says "Call again with offset=N and the same order=… to continue"; when it adds one, it says to call again from `offset=0` with the suggested order and continue by offset from there, and why. `nextOffset` stays the next offset under the caller's own order.

- **Empty pages at an offset** -- an empty page at `offset > 0` is either an offset past the end of a result set that matched, or a query that matches nothing, and with no result-set total the page alone cannot say which. The handler re-runs the caller's own clauses at `offset: 0, limit: 1` (two rows on the wire, with the over-fetch) and names the case: offset past the end when that probe returns a row, the no-match guidance when it returns none, both causes when the probe fails. Its failure is absorbed -- the empty page is already a correct answer.

  **Decision:** a one-row probe, spent only on this branch. The per-query `count(*)` rejected above is a different cost -- paid on every page, and a count over a grouped or aggregated query answers a different question. The probe asks the caller's exact query, so it holds for any `select`/`group`/`having`, and an empty page at `offset: 0` or any non-empty page issues no extra request. `format()` renders an empty page as a neutral `0 rows returned`; the cause lives in the notice, which reaches `content[]` through the enrichment trailer, so the two surfaces cannot disagree.

- **Row totals** -- `cdc_get_dataset_schema` and `cdc://datasets/{datasetId}` report a *dataset* total, a different question from the result-set total above and bought differently. The metadata document carries `cachedContents.count` on its first column, but Socrata builds that cache once and does not refresh it as rows land: measured live, `4va6-ph5s` cached 139,968 against 218,700 real rows and `9bhg-hcku` cached 88,128 against 137,700, while `bi63-dtpu` and `nr4s-juj3` matched exactly. A caller sizing a pagination walk against the stale figure stops a third of the way in, and `filter` assets such as `s2qv-b27b` carry no cached count at all.

  **Decision:** buy the live `count(*)` on the schema surfaces only, as an annotation that cannot fail the response it annotates. `SocrataService.getMetadata` issues it through `Promise.allSettled` alongside the metadata read rather than after it, and `rowCountSource` (`live` / `cached`) discloses which figure is in hand — a corrected number that does not say it was corrected is as misleading as the stale one. The request sends `$select=count(*)` and nothing else: naming a real column changes what Socrata groups over, so `$select=state,count(*)&$group=state` would silently answer with a count per state. A metadata failure still throws; a count failure is absorbed, leaving the cached figure and `rowCountSource: 'cached'`. The count also carries a 5-second deadline of its own, shorter than the 20-second request deadline, and is cancelled when either that or the caller's signal fires: by the time it is outstanding the metadata document has usually arrived, so a count held for the full request deadline would turn an optional annotation into a hang of the answer it decorates. The caller's own cancellation is the exception to "absorbed": it rethrows, since a call the caller ended is not a count that failed. Callers that want the column list and will discard the total -- `cdc_query_dataset`'s queryability probe -- pass `{ liveRowCount: false }` and spend one request.

- **Fieldless rows** -- `/resource/{id}.json` answers a `chart` or `map` ID with HTTP 200 and a body of empty objects, which reads as a paginated success carrying an invitation to keep paging. The row shape cannot decide it: SODA omits null keys, so a real dataset queried with a `select` whose columns are null on the matched rows serializes to the identical `[{},{}]`. Only the asset's column metadata separates the two -- the same `columns.length === 0` signal `cdc_get_dataset_schema` already keys off.

  **Decision:** probe metadata, but only from the degenerate branch -- every returned row carrying no fields, which an ordinary query never reaches, so no successful call pays for a second request. Zero columns fails `not_queryable`; columns present succeeds with a notice naming the projection as null on the matched rows. The `access_denied` entry names only `story`, `file`, and `href`: `chart` and `map` never 403, and naming them would send callers after an access decision that never happened. Guidance accumulates in a local array and is flushed through one `ctx.enrich.notice` call, because `notice` is last-wins and `ctx.enrich.truncated()` writes it too -- the projection notice and the truncation notice co-occur, and two writers would silently destroy one of them.

- **Blank input** -- form-based clients send every optional field they display, so an empty or whitespace-only string means "not set". Forwarded, it would change the answer: `query: "  "` sends `q=%20%20` and matches 0 catalog entries where an omitted `query` browses all of them; `select: " "` sends `$select= `, which projects nothing, so every row comes back fieldless, a metadata request is spent explaining it, and the notice blames the select clause `" "`; `tags: ["", "covid19"]` echoes the blank in `appliedFilters`.

  **Decision: a blank or whitespace-only optional string is unset, everywhere it is read.** `nonBlank()` in `src/utils/text.ts` is the one test. `SocrataService.query` and `.discover` apply it to every SoQL clause and catalog filter, and drop blank `tags` entries, so a direct service caller gets the same request; `cdc_query_dataset` and `cdc_discover_datasets` apply it once at the top of the handler, so the echoes, notices, offset probe, and near-miss lookup read the same normalized value. A value with any text in it is sent and echoed byte-for-byte, surrounding whitespace included -- trimming a SoQL clause is a rewrite of the caller's query. The schemas stay plain `z.string()`: a preprocess would also switch off the framework's lone-string-to-array repair on `tags`.

- **Upstream markup in prose** -- Catalog and metadata descriptions arrive as publisher-authored HTML and reach both response surfaces. Of 400 catalog dataset entries, 37 carry markup and 8 spend more than 60 of their first 300 characters on tags and inline CSS, so truncating before the markup comes off would put the ellipsis ahead of the first word about the dataset.

  **Decision:** one shared conversion in `src/utils/text.ts`, applied at each surface that shapes the text -- `toPlainText()` before `truncatePlainText()` cuts it, `getMetadata()` for the full-text surfaces -- and reused, segment by segment, for WONDER caveat/footnote/message text. Tags come off first and entities are decoded in a single left-to-right pass: a chained per-entity decode resolves `&amp;` before `&lt;` and turns `&amp;lt;` into `<`, manufacturing markup a publisher escaped so it would not be markup. The framework's `sanitization.sanitizeString` is not used: it re-escapes a bare `&`, and `sanitize-html` is an optional peer this server does not install. Numeric references are range-checked before decoding -- `String.fromCodePoint` raises a `RangeError` above U+10FFFF, and a lone-surrogate reference decodes to an unpaired code unit that Bun round-trips happily while `jq` rejects the whole frame -- so an undecodable reference stays literal text rather than being approximated.

  **Decision: WONDER keeps its links; Socrata does not.** WONDER caveats and messages end in a "More information." anchor to the methodology behind them, and stripping the tag would drop the destination from both response surfaces. The WONDER parser converts each anchor to a Markdown link on the raw markup, before any tag comes off, and decodes the text between anchors and each anchor's own text once apiece; the assembled string is whitespace-collapsed but never decoded again, so `&amp;lt;` still lands on `&lt;` and an entity-escaped anchor stays literal text. Hrefs are root-relative with spaces in their fragments (`#Assurance of Confidentiality`) and resolve against `https://wonder.cdc.gov/`, which percent-encodes the spaces; parentheses are encoded too so a `)` cannot close the link. Only an `http:`/`https:` result becomes a link — `URL` passes `javascript:` through — and a fragment-only or unparseable href keeps its text alone. `toPlainText` is unchanged, since a Socrata description has no link surface to carry. Anchors are found in one linear scan: an opener runs to the first `>` and on to the first `</a>` after it, and once an opener finds neither, no later one can, so the rest goes to the tag stripper as text. The rest of the response parser follows the same rule: every element (`<message>`, `<caveat>`, `<footnote>`, `<data-table>`, `<r>`, `<c>`) is found by a forward scan that pairs each opening tag with the first closer after it, as a lazy regex would, in time linear in the response.

  **Decision: tags come off in one linear scan, and a tag left open at the end comes off with them.** The Discovery API returns some descriptions cut mid-anchor near 4,000 characters (`jgk8-6dpn` and `n8mc-b4w4` end `<a href="https://…`), which `<[^>]*>` cannot match. `replaceTags` takes a tag from each `<` to the next `>`, exactly as that regex did; once a `<` has no `>` after it, no later one can either, so the scan stops and drops everything from the first `<` left open at the end: a comment opener, or a tag name, bare or carrying an attribute assignment, that runs to the end of the text. Prose with a `<` in it keeps its text -- `<5`, and also `x<y in women` or `<b grade or better`, which assign no attribute and do not end the text; a cut-open tag that is neither (`<input disabled`) reads as text too, the price of never dropping prose. The scan is linear in the length of the markup.

  **Decision: one cut rule for dataset descriptions, `truncatePlainText()`.** It cuts plain text -- after `toPlainText()`, so the budget buys visible text and no tag or entity can be split -- and appends `…`. GFM clients autolink bare URLs and extend one through a directly attached `…`, so `…https://www.iqvia.com…` would link to `https://www.iqvia.com%E2%80%A6`. A cut inside a scheme URL, `www.` host, or email address drops the partial address (a link to `https://www.cdc.gov/nch` is a link to a different page); a URL the cut lands right after is kept and set off by `" …"`; any other token is cut at the limit. A cut never splits a surrogate pair. `cdc_discover_datasets` applies it at 300 characters, and every other surface that shortens a dataset description uses the same function.

- **Markdown in `content[]`** -- `format()` renderers and enrichment trailer fields interpolate caller- and upstream-sourced text into Markdown. Left raw, `count(*)` in the query echo would pair into emphasis and vanish, a dataset name or SODA value carrying `<b>`, `*x*`, or `[label](url)` would render as markup, a caller's filter echoed in a notice would do the same, and a description opening `---` or `-|-|-` under the discovery metadata line would turn that line into a heading or a table header. `content[]` would then stop matching `structuredContent`.

  **Decision: escape at the render boundary, in `src/utils/markdown.ts`; `structuredContent` is never touched.** `escapeMarkdownText(value, slot)` backslash-escapes only what changes CommonMark/GFM rendering: `` \ ` * ~ [ ] | `` always (the backslash too, or `[x\](javascript:…)` would close a link), an underscore run unless a letter or digit sits on both sides (so `data_value_type` stays intact), `<` before a letter, `/`, `!`, `?`, or an email-autolink local part (so `< 1 year` and `<5` stay intact), and `&` before an entity reference. Line endings flatten to a space. GFM takes a bare URL's characters literally up to the next whitespace or `<`, backslashes included, so an escape inside that run lands in the link target (`county_geography-_changes2015.pdf` in `p56q-jrxg` would link to `…-%5C_changes2015.pdf`) and a trailing one re-arms (`https://x.org/a*` paired with a later `*`); a scheme URL whose run holds anything the escaper would touch is emitted as a CommonMark autolink, `<https://…>`, whose content renderers also take literally, cut back to the address GFM would have linked. Every other URL stays bare and byte-identical. A bare `www.` host has no scheme for that form and is escaped like its surrounding text. The `line` slot also escapes a leading block marker (`#`, `>`, `-`, `+`, `=`, `2000.`, `1)`) and drops leading whitespace that would open an indented code block; the `heading` slot escapes a trailing `#` run ATX would strip as a closing sequence. `escapeTableCell` is that escaper plus #24's newline collapse and trim, a normalization that runs in linear time. Query echoes and field names render through `markdownCodeSpan` / `markdownTableCodeSpan`, sized by the framework's `markdown().inlineCode()`, and every Socrata tool's `notice` renders through `markdownBlockquote`, which splits on the same line endings so a blank line in a caller's value cannot end the quote. The framework's `sanitization.sanitizeString` is not a fit: it strips tags rather than displaying them, re-escapes `&`, and needs the uninstalled `sanitize-html` peer. Tests round-trip through `marked` (a devDependency) rather than inspecting escaped strings, since only a real renderer shows what a client displays.

  Exempt, each for a stated reason: WONDER caveats and messages (CDC's own prose, already rendered to Markdown by `toLinkedText` with links that must stay live; the recorded responses in `tests/fixtures/wonder/` carry no active character outside those links), WONDER notices and `effectiveQuery` (built from validated enums, regex-checked ICD-10 codes, and CDC's messages), server-built fields (`updatedAt` on the schema surface, row counts, column keys WONDER defines), resources (`application/json`), the `analyze_health_trend` prompt, and error-message text. SoQL aliases are *not* exempt: SODA accepts `select state as _x_`, which renders as emphasis, so `cdc_query_dataset` escapes its header row too.

- **Wide schemas** -- Column counts across the catalog run from 3 to 322 (`ua7e-t2fy`, Weekly Hospital Respiratory Data). `cdc_get_dataset_schema` returns a window of 100 columns by default (`column_limit`; `column_offset` to continue). Selected columns keep their full descriptions -- descriptions carry the field semantics a caller needs to write a correct query, so the number of columns returned is the knob, never their content. The response discloses `totalCount`, `truncated`/`shown`/`cap`, and a `nextOffset` while columns remain, so no column becomes unreachable. `column_limit` has no maximum: it slices a schema already fetched whole, so no call returns more than the whole schema.

  The dataset-level `description` repeats on every column page, and paging cannot shrink it.

  **Decision:** cap the description at 4,000 characters by default on both `cdc_get_dataset_schema` and `cdc://datasets/{datasetId}`, cut with `truncatePlainText` after the markup comes off, and return it whole on `full_description: true`. A cut description carries `descriptionTruncated` and `descriptionLength`, and `content[]` names `full_description: true`; the resource, which takes no selector, names the tool in its `notice`, composed with the column notice. Column descriptions are never shortened. The cap shortens only the few dozen descriptions above it (longest ~59,000 characters, `3nnm-4jni`; median ~1,075). Leaving descriptions whole by default behind a flag that caps them was rejected: the caller cannot know a description is large until it has paid for it. `outlineOnOverflow()` was rejected too: over its 24,000-byte default budget it returns an outline in place of the payload, so the motivating call would get no columns back.

  **Decision:** the resource takes no selector. RFC 6570 query expansion (`{?column_limit,column_offset}`) expresses the URI, but the MCP SDK's `UriTemplate.match` compiles query variables into *required* pattern segments in declared order -- a template carrying them stops matching the bare `cdc://datasets/{datasetId}` form entirely, and a URI with only one of the two matches nothing. `cdc://datasets/{datasetId}` therefore applies the same 100-column default and 4,000-character description cap, discloses `columnCount`/`truncated`/`descriptionTruncated`/`descriptionLength` in its payload, and names `cdc_get_dataset_schema` as the selective surface. That keeps the URI every client already holds working, and leaves no unbounded path to the same data.

- **Catalog vocabularies** -- `category` and `tags` are matched against the Discovery API's own controlled vocabularies, and a caller cannot guess what is in them: a value one letter off returns an empty page, and advice to "try broader search terms" sends the caller after a problem that does not exist. Measured live against `data.cdc.gov`: `categories=Vaccinations` returns 89 entries and `categories=Vaccination` returns 0. Both vocabularies are published per domain -- `domain_categories` answers with every category (56 at the last measurement), `domain_tags` with every tag (1,582) -- and both allowlisted hosts return byte-identical results, as the one-tenant finding predicts.

  Two upstream details decide the shape. `domain_tags` caps a request that names no limit at 100 values **and reports `resultSetSize: 100` beside them**, so the under-count carries no signal that it is one; the service sends an explicit `limit=10000`, and `limit=100000` returns the same set, so that ceiling reaches the whole set rather than trading one silent cap for another. And the `categories` filter on catalog *search* only applies when `search_context` accompanies `domains` -- `?domains=data.cdc.gov&categories=Vaccinations` alone returns 0. `discover()` already sends it; the vocabulary endpoints do not need it, and sending it changes nothing.

  **Decision:** the service fetches each vocabulary whole -- correct counts and near-miss matching both need the full set -- while `cdc_list_catalog_vocabulary`'s own response is bounded and says so. Categories return whole (a few dozen values, ~3 KB); tags are ranked by entry count and paged at 50 by default, because the full set costs ~66 KB of `structuredContent` plus ~36 KB of rendered text, roughly 25k tokens in one call. The distribution is what sets the default (measured October 2026 on `data.cdc.gov`, 1,582 tags): 33 tags carry 50 or more entries, 108 carry 20 or more, and 635 carry exactly one, so a page of 50 reaches down to 39 entries -- the head a caller is actually choosing a filter from. Measured on the wire, the default response is 5,575 bytes of `structuredContent` and 3,495 bytes of `content[]` text. Paging alone would leave a caller hunting one value blind across ~1,600 rows, so `filter` narrows both vocabularies *before* the page is cut; ranking by count makes the smallest value shown a rigorous upper bound on every tag after the page, surfaced as `truncationCeiling`. The bound covers the tail only: on a page past `tag_offset` 0 the tags before it rank at or above the first tag shown, so the field description and its `content[]` label (*Max Entries per Tag from nextOffset On*) both scope it to the tags from `nextOffset` on. `tag_limit` has no maximum -- it slices the vocabulary already fetched, and the whole set serializes to about 118,000 characters -- so the paging notice offers a larger `tag_limit` whenever tags remain.

  **Decision:** the near-miss notice names candidates, it does not retry the query. Matching (`src/utils/vocabulary.ts`) is token containment in both directions -- every filter token inside some value token, which resolves "Vaccination" to "Vaccinations", or every value token inside the filter, which resolves "nndss weekly" to "nndss". A token under three letters or digits matches only an equal token, whether it comes from the filter or from a value: containment stops discriminating below that ("a" sits inside most tags), so `tb` reaches the word `tb` in `tuberculosis (tb)` and never `outbreak`, and the `19` of `covid-19` never relates to `2019`. A filter with no letters or digits names nothing and matches nothing. `cdc_list_catalog_vocabulary` reads a short filter that matches nothing as ignored rather than as a miss, since matching whole words only says nothing about its spelling. Deliberately not fuzzy: a transposed spelling resolves to nothing and the caller is pointed at the vocabulary tool, because an approximate guess commits them to a value they never typed. The lookup runs only from the empty-page branch of a `category`/`tags` search -- never for a non-empty page, a free-text-only search, or an offset past the end -- so an ordinary discovery call issues no vocabulary request. It annotates an answer that is already correct, so its failure is absorbed and the discovery result stands.

- **Error classification** -- `SocrataService.fetchJson` is shared by every Socrata definition (both catalog consumers, both metadata consumers, the vocabulary tool, and the query tool), and each handler re-dispatches on `err.data.reason` alone, discarding the HTTP-derived code. A reason therefore has to be true for every status it covers, and has to be declared by every consumer that can raise it — `ctx.fail` with an undeclared reason returns an `InternalError` whose data carries the full declared-reason list to the caller. Statuses observed live against both portals:

  | Status | Endpoint | Trigger | Permanent? | Reason | Code |
  |:---|:---|:---|:---|:---|:---|
  | 400 | `/resource`, catalog | Malformed SoQL, unknown column, type mismatch, `offset + limit > 10000` | Permanent | `invalid_query` / `no_such_column` / `type_mismatch` | ValidationError |
  | 403 | `/resource` | `story` / `file` / `href` asset ID | Permanent | `access_denied` | Forbidden |
  | 404 | `/api/views`, `/resource`, catalog | ID or endpoint does not exist | Permanent | `dataset_not_found` | NotFound |
  | 429 | any | Rate limiting | Transient | `rate_limited` | RateLimited |
  | 5xx | any | Upstream outage | Transient | `upstream_error` | ServiceUnavailable |
  | no status | any | Unreachable (network, DNS, TLS), body cut off mid-transfer, no complete answer within the 20-second deadline, a 2xx body that is not JSON or fails the endpoint's body schema | Transient | `upstream_error` | ServiceUnavailable |
  | other 4xx | any | Unobserved (401, 410, 451, …) | Varies | none — bubbles with the framework's own classification | per status |

  `upstream_error` covers a failed HTTP status only for a 5xx, and otherwise only a request that never yields a readable body, because it is the only reason marked retryable; a 403 routed through it would tell callers to retry a permanent refusal and to expect the portal was down. A 2xx body is read through a schema per endpoint, since a lenient read lets an edge error page or `{"message":"ok"}` pass for an empty catalog page or a non-tabular asset. The caller's own cancellation is none of these: it rethrows exactly as it arrived. Statuses outside the table carry no reason at all, so the handlers rethrow them and the framework's status mapping survives instead of being flattened into a reason that is not true. `not_queryable` and `page_out_of_range` are raised in handlers rather than by the service, so they appear in no row above; `chart` and `map` IDs answer 200 and are caught by the fieldless-rows branch, never by the 403 row.
